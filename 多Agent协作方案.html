一句话结论：「三省六部」在多 Agent 语境下最明确的对应项目是 Edict（cft0808/edict）——它不是一个能 import 进自己程序的 Python 库，而是一套基于 OpenClaw 的多 Agent 编排系统加实时看板：把唐朝「中书决策、门下审核封驳、尚书执行、六部分工」硬编码成 Agent 分工、单向权限矩阵和状态机，专治自由群聊式多 Agent 的跑偏、不可审计、不可干预。

它的最大卖点也是最大代价：强制审核 + 全程可观测可干预，换来的是 12 个 Agent 轮番调用大模型的 token 与延迟成本，和对 OpenClaw 部署的依赖。对独立 Python 开发者做小工具，最实用的起点是 LangGraph（要可控、可调试的工作流）和 smolagents（要最轻、最透明的代码执行），第二梯队是 CrewAI（快速拼一个角色小队）。

三省六部：Edict 是什么

历史原型是隋确立、唐完善的中央制度：中书省草拟政令、门下省审查诏令并有权驳回、尚书省执行政令并统领六部（吏、户、礼、兵、刑、工），三省分工制衡。Edict 搬进 Agent 编排的核心思想只有一条：不是让几个 Agent 自由聊天，而是让流程本身不允许跳过审核。

你在飞书 / Telegram / Signal 里「下旨」
→
太子分拣：闲聊直接回，真旨意才建任务
→
中书省规划：拆解子任务、设计方案
→
门下省审议：准奏，或封驳打回重做
→
尚书省派发：协调六部、汇总结果
→
六部并行执行各自的活
→
回奏结果归档为「奏折」

任务状态机：分拣 → 规划 → 审议 → 已派发 → 执行中 → 待审查 → 已完成；被封驳就回到规划重做。scripts/kanban_update.py 内置合法跳转校验，非法跳转（如 Doing→Taizi）会被拒绝并记日志——流程不允许「跳步」。

它和「群聊式框架」最根本的四点区别

  • 不是自由群聊，是单向权限矩阵。太子只能发给中书；中书可回太子、发门下和尚书；门下可回中书、发尚书；尚书可回中书 / 门下、发全部六部与吏部；六部只能回尚书。下级不能越级喊话，上级不能绕过审核直达执行层。
  • 审批是强制关卡，不是可选插件。每个旨意都必须过门下省：规划不完备、拆解不合理就封驳打回，强制返工直到达标。README 自述对比称 CrewAI「无」专职审核、AutoGen 只有 Human-in-loop——注意这是项目方的宣传口径，不是对竞品的客观评测。
  • 通信分两层。Agent 层走 OpenClaw 原语（sessions_spawn / sessions_send / 公共频道消息），每个 Agent 有独立 Workspace、Skills 和模型，角色规则写在 agents/<id>/SOUL.md 里，改 Agent 就是改这个文件；后端服务层走 Redis Streams 事件总线 + 事务性 Outbox 中继（至少一次投递），支持并行调度、指数退避重试、资源锁与 DAG 依赖解析，所有状态变更写审计日志。
  • 人可以随时干预，但「人审批」还不是标配。看板支持叫停 / 取消 / 恢复任务、Agent 健康监控与 Token 排行榜；但 Roadmap Phase 2 还在做的「御批模式」（人工一键准奏 / 封驳）说明：目前审批主力是门下省这个 Agent，人工审批是计划中的功能，别误以为开箱即是人工审批流。

两个容易混淆的点：

① 仓库 About 栏写的是「9 specialized agents」，README 正文写的是「12 个 AI Agent（11 个业务角色 + 1 个兼容角色）」——本页以 README 正文的 12 个为准。

② 另一个项目 wanikua/danghuangshang 也是 OpenClaw「AI 朝廷」配置包，但默认是明朝内阁制（司礼监—内阁—六部—都察院），唐三省只是它的可选配置之一。2026 年 3 月的英文报道里，「三省六部」指的都是 Edict，不是它。

适合与不适合

  • 适合：需要「计划先被独立审核、执行全程可看可停可审计」的个人 / 小团队助手场景——周报与数据报告、竞品分析、代码审查（兵部写、刑部审）、API 设计与文档、多步骤调研汇总；尤其适合已经在用 OpenClaw、想给助手套一层制度外壳的人。
  • 不适合：嵌进自己 Python 工具的可编程工作流（它没有库 API）；对延迟和 token 成本敏感的批量小任务（12 个 Agent 全流程开销明显）；需要严格 SLA 和长期维护保障的生产系统（近半年无提交、单人维护色彩较重）。

外部评价也印证了这笔交易：2026-03-11 的英文长文称其为「12 Agent + 铁权限矩阵 + 单向信息流」，并点出核心代价——每一步起草、审核、否决、重做都要烧 token，是「用速度和便宜换幻觉更少的可靠性」（Substack 长文）；36氪英文版 2026-03-10 报道时其 Star 已超 6,500（36Kr）。两者都不是性能基准测试，只能说明「爆红快、理念鲜明」。

点任意一个角色看它的职责和对应的历史职能。README 的口径是「12 个 Agent = 11 个业务角色 + 1 个兼容角色」，其角色清单实际具名的是下面这 11 个：太子、三省、户 / 礼 / 兵 / 刑 / 工五部、吏部、早朝官——吏部本属传统六部之一，README 又把它单列进「七部」表述，计数口径本身略有含混，这里如实标注、不替它凑数。

和其他成熟框架对比

Star 数均为 2026 年 9—10 月前后的第三方快照，不同来源、不同日期会有数千差异，只用来看量级，别当实时精确值。CAMEL 与 AgentScope 未找到同口径的可靠 Star 数字，故不写精确值。

一个容易踩的坑：Star 数 ≠ 活跃度。Edict 有 17k Star，但最新提交在 5 个月前；MetaGPT 的 Star 在最高一档（65k—71k 量级，两个快照口径不同），但最新稳定版停留在 2025-03-09 的 v0.8.2，后续只是修修补补，2026 年的活跃度统计把它的最后提交记为 2026-01，团队重心已转商业产品 MGX，且当前版本只支持 Python ≥3.9 且 <3.12。

选型时除了 Star，还要同时看四件事：最近提交时间、有没有 Release、Issue 是否有人回、是否支持你现在的 Python 版本。这四项里，Edict 和 MetaGPT 都不算顶格。

肆

五种协作模式与权衡

多数框架是混用几种模式，不是单选。Edict 本身就是「层级审批 + 流水线 + 并行执行」的复合体：先走中书→门下的审批流水线，再由尚书把任务扇出给六部并行跑——这正是它比纯主管模式多两层开销的原因。

模式怎么协作代表实现适用场景
中央 Supervisor（主管—工人）一个主管 Agent 拆任务、派给专家、汇总结果；工人只见自己的简报、回结果LangGraph supervisor、CrewAI hierarchical、Google ADK 根 Agent 委派、Edict 的尚书省（但 Edict 在主管前还加了规划与审核两层）任务结构事先说不清、需要动态选专家，且需要一个明确汇总点
流水线 Pipeline（顺序）Agent 按固定顺序接力，前一个的输出就是下一个的输入MetaGPT 的 SOP、CrewAI sequential、ADK SequentialAgent、LangGraph 线性图流程固定、可复现：调研→写作→审校，需求→设计→代码→测试
层级审批（Hierarchical Approval）在流水线 / 主管之上再加一道独立审核关：规划者与审核者分离，审核者有权否决打回Edict 的中书→门下→尚书是最极致的例子；LangGraph 的人工 interrupt、MetaGPT 的 QA 环节是弱化版质量 / 合规 / 安全的代价高于速度的场景；但要接受返工循环拖长流程
对等辩论 / 群聊（Peer Debate）多个 Agent 平等对话、互相批评，或正反方辩论后由裁判 / 投票定稿AutoGen GroupChat、CAMEL 角色对子、Edict 的「朝堂议政」、多 Agent 辩论研究范式答案不唯一、需要多视角纠错的高风险推理；研究与评审类任务
对等交接 / 蜂群（Handoff / Swarm）没有中央主管，当前 Agent 自己决定下一个交给谁，点对点移交LangGraph Swarm、OpenAI Agents SDK handoffs、ADK 的 sub_agents 动态路由（弱化版）路由逻辑简单、Agent 间职责边界清晰的转交场景；比群聊省上下文
模式复杂度成本（token / 延迟）可靠性可调试性主要风险
单 Agent（对照组）最低最低取决于单模型与提示词，无交叉校验最好：一条链路上下文爆炸、幻觉无人纠
流水线低—中：顺序写死低—中：每步一次调用中：每步可加校验，但一步错会向后传导好：步骤与产物一一对应僵化；中途需求变化要改流程
中央 Supervisor中：主管提示词是关键中：主管每次都要读汇总再决策中—高：能重试 / 换人，但主管是单点中：主管决策链可追踪，工人内部仍是黑盒主管瓶颈、主管错则全错、上下文汇总失真
层级审批（Edict 式）高：角色、权限、状态机三套规则最高：规划+审核+执行+可能的返工循环，每轮都烧 token高（对计划质量而言）：坏计划很难流到执行层好（流程层面）：看板 + 审计日志能还原谁批了谁；但单个 Agent 的推理仍难复现审核过严→无限返工；审核 Agent 本身幻觉→误杀好方案；制度成本压倒小任务收益
对等辩论 / 群聊中—高：发言顺序、终止条件难调高：多 Agent 各说各话，历史越滚越大中—高（对事实性任务）：多视角能纠错，但也可能互相附和差：要翻整段对话才能定位谁带偏了无限寒暄 / 互相附和 / 死循环；没有终止规则会一直聊下去
对等交接 / 蜂群中：交接条件要写清楚中：省去主管中转，但每次交接仍要重述上下文中：边界清晰时很顺，模糊时容易踢皮球中：交接链可追踪，但无全局视图循环交接、责任不清
  • 结构化换可靠性，涌现式换灵活性。图 / SOP / 审批这类结构化编排换来可靠性与可审计性，代价是前期设计成本；群聊 / 角色扮演这类涌现式编排反过来。（MDPI 综述）
  • 状态模型决定你能怎么排错。LangGraph / 微软新框架把状态当一等公民（类型化、可 checkpoint、可回滚）；CrewAI / AutoGen 的状态更多是从对话历史中「长出来」的，短任务简单，长流程容易失控。
  • 先用最轻的模式解决真实失败。只有当你能说出「单 Agent 具体在哪个环节失败、需要哪个新角色来补」时才加 Agent；否则每加一个 Agent，都是在加 token、延迟与调试面。Edict 的反面教材意义正在这里：它默认给你 12 个 Agent，哪怕你的任务只需要 2 个。
伍

给独立 Python 开发者的选型

场景限定：一个人、用 Python、做小型自动化工具——代码生成、测试、数据处理、网页自动化。不是做平台、不是带团队、不是发论文。先用下面的小测试对一下号，再看展开。

你的工具，逻辑主要是哪一种？

第 1 位 · 默认答案

LangGraph

需要「可控工作流」时的首选，也是目前 Python 生态里最不怕变复杂的起点。开始可以只是一个 ReAct Agent；后来需要「生成→测试→修 bug→再测」的循环、人工确认危险操作、断点续跑时，不用换框架，直接在图上加节点和边、加 checkpoint 就行。状态、重试、人工介入（interrupt）都是现成的，出了问题能定位到某一步、某一次状态变更，而不是只剩一段聊天记录。

对应你的任务：代码生成（生成→测试→修复循环）、数据处理（抽取→清洗→校验→落盘，每步产物可查）、网页自动化（导航→抽取→校验→重试，失败可从 checkpoint 恢复）。

代价：样板代码比 CrewAI 多，要自己设计状态结构；别一上来就写 supervisor 多 Agent，先单 Agent + 工具 + 循环，真的需要分工时再挂子图。

GitHub 仓库官方文档
第 2 位 · 最轻最透明

smolagents（Hugging Face）

核心约 1,000 行、Apache-2.0。它的 CodeAgent 让模型直接写 Python 代码调用你的工具函数——工具就是普通 Python 函数，Agent 的每一步都是可读的代码，调试时不用猜框架在背后做了什么。pip install smolagents 几行就能跑，模型可换 LiteLLM / 本地 Ollama / HF。

对应你的任务：批量数据清洗与报表、调用 API / 爬取并结构化、把重复手工操作写成「Agent + 一组工具函数」的小脚本。

注意：代码执行必须加沙箱（E2B / Modal / Docker，或至少只在受信本地环境跑）；它本身不是多 Agent 框架，复杂协作要自己拼，别指望它替你做编排。

GitHub 仓库官方文档
第 3 位 · 可选捷径

CrewAI

最接近「用人话组建团队」：给每个 Agent 写 role / goal / backstory，给每个 Task 写描述与期望输出，Crew(...).kickoff() 就跑起来，20 行左右能跑通一个小队。sequential 是流水线，hierarchical 会自动生成一个经理 Agent 做委派与校验；另有 Flows 做事件编排。现成工具也较多（搜索、读文件、读 PDF 等）。

什么时候选它：流程基本固定、分支少，你更看重「今天就能跑起来」。

什么时候别选它：流程里有循环、条件分支、需要精确状态回放时——经理 / 委派逻辑是黑盒，那时 LangGraph 的图好维护得多。

落地清单：避开多 Agent 的常见坑

先写确定性代码（解析、校验、测试、落盘）包住不确定性：让 Agent 只做「生成 / 判断」，让 Python 代码做「执行 / 校验 / 重试」。
每个 Agent 只给一个可验收的交付物——例如「输出一段能通过 pytest 的代码」，而不是「提高代码质量」。
给循环设硬上限（最多修 N 次、最多辩论 M 轮），防止返工 / 辩论循环烧光 token。Edict 的门下省封驳循环如果没有上限，在小任务上就是这个坑的放大版。
危险操作（删文件、发请求、改线上数据）前加人工确认或白名单；框架的 interrupt / 审批是用来兜底的，不是装饰。
记 token 与延迟账本：多 Agent 的第一性价比指标不是「Agent 数量」，而是「每完成一个任务花了多少 token、多少秒、失败率多少」。
